# AvoidAnonymousTypes migration

## 1. Conclusion and scope

`@azure-tools/typespec-azure-core/no-unnamed-types` provides **partial, not functionally equivalent**, coverage of the [AvoidAnonymousTypes Swagger linter](https://github.com/Azure/azure-openapi-validator/blob/6243cb01c16c7535cd3b8df6f45fbeb3c095ed7f/docs/avoid-anonymous-types.md). The TypeSpec linter checks authored anonymous types, including implicit HTTP responses; it does not reproduce Swagger schema inlining for named dictionaries, `allOf` or schema overrides.

## 2. Actual coverage

**Historical Swagger/TypeSpec comparison:** of 468 ARM projects, **462 compiled successfully**. The six failed projects and their 22 Swagger findings were excluded from the comparison and remain unassessed. The table counts individual diagnostics in those 462 successful projects. Its TypeSpec result is from the former **response-only** `tsp-lintdiff-local-linter/avoid-anonymous-types`, not the complete consolidated Core rule.

| Count in the historical 462-project comparison | Swagger linter | TypeSpec linter |
| ---------------------------------------------- | -------------: | --------------: |
| Raw diagnostics                                |             10 |               1 |

**Assessed coverage:** all 10 Swagger findings were explained by named dictionaries being represented inline: three response dictionaries, three nested dictionaries and four dictionary-valued properties literally named `additionalProperties`. The one TypeSpec-only finding was an anonymous SDK override outside the emitted HTTP operation population. These are **different findings, not 10 missed anonymous source declarations or one matched violation**. Focused tests establish the response behaviors in section 3, but neither this comparison nor those tests establishes a complete Swagger-to-TypeSpec match. A coverage percentage and current-corpus frequencies of composition/extension differences remain **unassessed**.

**Current external CI:** **604 projects passed and one failed, out of 605 attempted**. The failure contains one naming warning, promoted to an error, at the CustomLocations SDK override. This confirms the response check reports that target at the current linter/compiler revision. It is a rollout check, **not a Swagger/TypeSpec comparison**, so its result is separate from the table above. One diagnostic maps to one source target and one proposed suppression; see the [CI causality report](compatibility.md).

**Historical warning-impact experiment:** all **469 source compiles succeeded**, while the complete naming rule produced **21 baseline versus 22 candidate warnings**. Only CustomLocations was added; none were removed. This measures the warning increase, not Swagger coverage. Both historical measurements predate later rule/compiler changes and must not be presented as current-head comparisons. See [diagnostic-count differences](#4-why-diagnostic-counts-differ); the [evidence appendix](evidence-details.md#assessed-inputs-and-counting) pins the inputs for each measurement.

The table explains the **10-versus-one historical comparison** from section 2. `raw / grouped` means Swagger diagnostics / distinct project + Swagger-file + JSON-path locations; no occurrences collapse. The TypeSpec column counts response-only findings for that context, not unrelated warnings from the complete Core rule. Current CI confirms the last row's compatibility effect but does not add another finding to these historical totals.

| --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------: | --------------------------------------: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Three response dictionaries](evidence-details.md#dictionary-representation-differences)                                    |                               3 / 3 |                                       0 | Preserve supported named `Record<T>` authoring. Exact schema-inlining parity would need a separate policy decision, not a blanket anonymous-model warning.                                                                                                                                          |
| [Three nested dictionaries](evidence-details.md#dictionary-representation-differences)                                      |                               3 / 3 |                                       0 | Retain the source-naming boundary; do not treat a named generic dictionary as an unnamed declaration.                                                                                                                                                                                               |
| [Four dictionary-valued properties named `additionalProperties`](evidence-details.md#dictionary-representation-differences) |                               4 / 4 |                                       0 | Preserve the dictionary policy. These selector matches are not evidence of four anonymous source-model violations; no upstream-bug disposition is claimed.                                                                                                                                          |
| [CustomLocations SDK override](evidence-details.md#sdk-override-and-compatibility)                                          |                               0 / 0 |                                       1 | [Draft compatibility proposal #48088](https://github.com/Azure/azure-rest-api-specs/pull/48088) adds one operation-scoped suppression to preserve the existing JavaScript response contract. This is a proposed remedy, not approval, validation or landing; the original linter CI remains failed. |

**The counts do not cancel:** seven historical projects contribute 10 Swagger-only findings, and a different project contributes one TypeSpec-only finding. The remaining [composition/extension differences](evidence-details.md#composition-and-extension-boundary) have source-backed explanations but no measured corpus frequency. The [suppression proposal](compatibility.md#suppression-scope) addresses the confirmed compatibility target only; it does not close these policy differences or establish a new Swagger comparison.
