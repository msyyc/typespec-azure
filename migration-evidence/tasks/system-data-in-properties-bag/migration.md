# SystemDataInPropertiesBag migration

## 1. Conclusion and scope

Extend the existing TypeSpec rule `@azure-tools/typespec-azure-resource-manager/no-reserved-resource-property` with `systemData`; do not introduce `no-nested-system-data`.
This supplies **partial native coverage** of Swagger rule [SystemDataInPropertiesBag](https://github.com/Azure/azure-openapi-validator/blob/e1b8b207a196cf2fc288593efec22e6e38ab98d5/docs/system-data-in-properties-bag.md), not strict functional equivalence.

The accepted native policy checks immediate and inherited members of recognized ARM resource properties models, keeping system metadata in the resource envelope. It uses the existing rule's case-insensitive authored TypeSpec names, diagnostic targets and activation. It does not recursively inspect arbitrary nested objects, collections or embedded resource envelopes, or resolve JSON aliases. The existing `billingData` check is unchanged.

This intentionally replaces the earlier proposed recursive policy. [ARM guidance](https://github.com/Azure/azure-resource-manager-rpc/blob/8231d7df51aec87e6ccb5bcc04478136758b0a4c/v1.0/common-api-contracts.md#system-metadata-for-all-azure-resources) places system metadata in each resource's envelope; nesting an embedded resource envelope does not by itself establish misplaced metadata. The user approved this narrower policy and consolidation after reviewing the actual source witnesses and the activation consequences. Other nested placement problems are outside this native check, not universally declared compliant.

## 4. Why diagnostic counts differ

**DataBoxEdge remains 0/1.** `DataBoxEdgeDeviceProperties.systemData` at `models.tsp:1447:3` is a direct member of the standard tracked resource's bag, present in the selected `2023-12-01` `Devices_Get` response schema. The original source/schema witness still applies to the new rule's exact target. The pinned Swagger helper can stop after its first nonmatching child because it treats an empty result array as truthy. This is a code-backed false-negative explanation, not a newly captured Swagger trace. [Evidence and disposition](differences.md#databoxedge-direct-bag-metadata).

**AzureDataTransfer changes from historical 0/1 to current 0/0.** The previous recursive rule reported `ReadPipelineConnection.systemData` below `PipelineProperties.connections[]`. That element has its own `id`, `name`, `type`, `systemData` and `properties` envelope. Its nesting alone is not sufficient to classify its metadata as misplaced. Removing this warning is the authorized scope correction, not an unexplained missing diagnostic. [Evidence, historical receipt and regression link](differences.md#azuredatatransfer-embedded-connection-envelope).

Comparing every historical and current project row found no other count changes. The raw Swagger/native gap decreases from 0/2 to 0/1. **Native counts are not unchanged**, and zero Swagger findings cannot prove exhaustive parity or that no possible Swagger-positive case is excluded.
